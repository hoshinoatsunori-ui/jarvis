音声は入口から出口まで 16bit 符号付きリトルエンディアン・モノラル PCM のまま流れる。Whisper 系 STT もウェイクワード検出器も 16 kHz を前提にしているので、段の間で形式変換が起きない。

各段の間を何が流れるかが、そのまま差し替えの境界になっている。たとえば STT を faster-whisper から OpenAI に替えても、前後の段は「発話音声が来て、テキストを返す」以上のことを知らない。

矢印の上の語が、その境界を越えるデータ。この粒度が各段の差し替え可能な単位になっている。
02 / Rationale

音声から音声を直接生成する S2S ではなくカスケードを採ったのは、日本語の STT と TTS をローカルに置いたまま、LLM だけクラウドにする構成が取れるため。音声が家庭外に出るのはウェイクワード検出後だけ、という設計にできる。

代わりに割り込み（barge-in）は自前で実装することになる。現時点では未実装。

S2S との比較
観点S2S（Realtime / Live API）カスケード（本実装）
レイテンシ最小。中間ハンドオフが無い各段の合算。ストリーミングで短縮
割り込みネイティブ対応自前実装が要る 未実装
カスタマイズ性低い。LLM も音声もベンダー固定高い。各段を差し替え自由
LLM 切替不可（音声パスに固定）自由
音声の所在常にベンダーへ送るローカル完結にできる
この選択が効かなくなる条件 「S2S の手軽さ」を取るなら、この実装は土台にならない。pipeline.py を Realtime API のセッション管理に置き換えることになり、段の抽象はほぼ残らない。

待受から発話までの一巡。VoiceLoop が 1〜4 を、Conversation が 5〜7 を持つ。テキスト対話（jarvis chat）は 5 から入るだけで、後半は音声と同じ経路を通る。

01

フレームを溜めてウェイクワードに食わせる

マイクは 30 ms 単位で読むが、検出器が要求する単位（openWakeWord なら 80 ms）は違う。間にバッファを挟んで再分割する。同時に直前 300 ms を保持し続ける。

pipeline.py — run_on_frames
02

検出したら、保持していた 300 ms を先頭に録音を始める

検出の瞬間から録り始めると語頭が欠ける。プリロールを足すことで「ジャービス、あしたの天気」の「あ」が残る。

pipeline.py — _record
03

VAD で発話の終わりを見つける

声が始まるのを待ち、800 ms の無音が続いたら切る。声が来ないまま 6 秒経ったら諦めて待受に戻る。20 秒を超えたら打ち切って STT に回す。

pipeline.py — _record
04

STT にかける。空なら何もしない

物音でウェイクワードが誤検出されると空文字が返る。ここで止めることで、LLM に無意味な呼び出しが飛ばない。

pipeline.py — _handle
05

LLM にストリーミングで投げ、ツール呼び出しを回す

tool_use が返ったらツールを実行し、結果を 1 つのユーザーメッセージにまとめて返して続行。並列呼び出しの結果を複数メッセージに分けると、モデルが並列呼び出しをしなくなるため必ずまとめる。

llm.py — AnthropicAgent.respond
06

届いたトークンを文に切る

句点・感嘆・疑問・改行で切る。60 文字を超えても文末が来なければ読点で切る。8 文字未満の断片は次とまとめる（「はい。」だけで合成を呼ぶと、かえって発話が細切れになる）。

textutil.py — iter_sentences
07

1 文できるたびに合成して再生する

応答が出揃うのを待たない。最初の音が出るまでの時間は、全文の生成時間ではなく最初の 1 文の生成時間で決まる。

「エンジン名 → 実装」の対応表は factory.py の 1 箇所だけ。段を足すときはここに 1 行足す。import は呼ばれたときに初めて行うので、使わないエンジンの重い依存（faster-whisper、onnxruntime）が起動を遅らせることはない。

依存が足りないときは EngineUnavailable が「何が無いか」と「何を入れれば動くか」を持って上がってくる。jarvis doctor はそれを拾って一覧にする。

LLM が呼べるツールは 2 種類ある。組み込み（get_current_time / remember / recall / forget）と、設定に書いた MCP サーバのツール。どちらも同じ ToolSpec に変換されるので、LLM 側から見れば区別がない。

ツールの失敗で会話は落ちない。例外は捕まえて is_error 付きの結果としてモデルに返し、判断させる。

MCP の Python SDK は asyncio 前提だが、パイプライン本体は同期で回っている。専用スレッドでイベントループを 1 本持ち、各サーバの接続は 1 つの常駐タスクが開いたまま保持する。async context manager は入ったタスクと同じタスクで抜ける必要があるため、接続と切断を別々の呼び出しに分けられない。

同期側は Future を待つだけ。接続の寿命は常駐タスクが持つので、呼び出しごとの接続確立は起きない。
# config.yaml — MCP サーバを足すと、その場でツールが増える
tools:
  builtin: true
  mcp_servers:
    filesystem:
      command: npx

体感を決めるのは応答全体の長さではなく、最初の音が出るまで。そこだけを狙って 3 つ決めている。

文単位で TTS に渡す

応答が出揃うのを待たず、1 文できた時点で合成を始める。文末が遠いときは 60 文字で見切って読点で切る。

effort を下げる

雑談や家電操作に深い推論は要らない。思考の深さを浅くして応答を早める。

thinking は無効化しない

Claude Opus 5 で thinking を無効にすると、ツール呼び出しを tool_use ブロックではなく本文テキストに書いてしまう既知の失敗モードがある。呼び出しが実行されないまま会話が進むため、エージェントとしては致命的。速くしたいなら effort を下げる。

この判断のぶんだけ、応答開始は遅くなる

remember で保存した事実は JSON に残り、次回以降システムプロンプトに差し込まれる。システムプロンプトは不変のペルソナが先、毎回変わりうる記憶が後という順で組む。プロンプトキャッシュは前方一致なので、この順序を入れ替えると効かなくなる。

件数が増えて効かなくなったら、Memory.as_prompt_block() をベクトル検索に差し替える。それが今のところの拡張点。

会話履歴を切り詰めるときは、ツール結果が孤立しない位置で切る。tool_result だけが先頭に残ると API が受け付けない。

設定は YAML 1 枚。各段は engine と options という同じ形をしていて、差し替えるときに触るのは engine の 1 行だけ。値の中の ${VAR} は環境変数に展開される（${VAR:-既定値} も書ける）。API キーを YAML に直接書かないための仕組み。

テストはハードウェアに依存しない。パイプラインは偽のフレーム列を流し込んで検証し、LLM は SDK を差し替えて「ツールを実行し、結果を正しい形で返すか」を見ている。MCP ブリッジだけは実際に子プロセスの MCP サーバを起動して確かめている——ここは偽物で代替すると、検証したいスレッド境界がそのまま消えてしまうため。
