# 自作Jarvis 第4回 — TTS をローカル日本語に差し替える

第3回の末尾で予告したとおり、TTS（音声合成）を OS 標準から日本語ローカルのエンジンに差し替えました。

これも、第3回と同じく**今回は実装していません**。コードは Phase 0 のときに書いてあったので、やったのはアプリをインストールして `config.yaml` を書き換えることだけです。それでも、聞き比べて選ぶところと、どちらを選んでも消えない設計の話は書いておきたいので、残します。

コード: https://github.com/hoshinoatsunori-ui/jarvis

---

## なぜ差し替えるのか

OS 標準の音声合成（Windows なら SAPI、macOS なら say、Linux なら espeak-ng）は、依存ゼロで動くという大きな利点があります。第1回ではまずこれで通しました。

ただ、ジャービスという装置を家に置くとなると、2 つ気になります。

**ひとつ、自然さ**。Windows SAPI の日本語音声は、短い指示には十分でも、2 文、3 文と続く応答を聞いていると、どこかで「機械が喋っている」感じが前に出てきます。

**ふたつ、キャラ**。これは言語化しにくい話なのですが、「ジャービスはこういう声で喋る」というイメージが先に決まると、短い返事でも装置らしさが立ちます。SAPI だと「どの OS で動かしても同じ無個性な声」になりやすい。

ローカルで動く日本語 TTS で広く使われているのは 2 つです。

- **VOICEVOX**: 広く使われている。キャラが多い。生成が軽い
- **AivisSpeech**: Style-Bert-VITS2 ベース。より表情豊か。生成はやや重い

どちらも**同じ VOICEVOX 互換 REST API** （`/audio_query` → `/synthesis` の 2 段）で喋らせられます。ポートが違うだけ（VOICEVOX が 50021、AivisSpeech が 10101）。

---

## 入れ替えの手順

両方ともインストーラ経由の GUI アプリです。それぞれダウンロードして入れて、起動すると裏で HTTP API が立ち上がります。ポートが別なので同時に起動しておけます。

Jarvis 側は `config.yaml` の `tts` を書き換えるだけです。コード変更ゼロ。

```yaml
tts:
  engine: voicevox   # AivisSpeech も同じ engine 名で OK
  options:
    base_url: http://127.0.0.1:50021   # AivisSpeech なら 10101
    speaker: 13                        # 話者 ID
```

話者 ID は `GET /speakers` で引けます。VOICEVOX は 40 人超（スタイル違いを含めると 100 以上）、AivisSpeech は 2 人（スタイル違いで 10）。

`engine: voicevox` のまま `base_url` だけ変えて AivisSpeech に飛べるのは、第1回で書いた「各段を差し替え自由」の設計がちゃんと機能している証拠です。実装クラスがひとつ、HTTP API が同じ形、それだけ。

## 聞き比べて選んだ

今日やった聞き比べは 4 本です。

1. VOICEVOX / 四国めたん（ノーマル） — 可愛い女性声、はっきり
2. AivisSpeech / Anneli（ノーマル） — 柔らかい女性声、表情あり
3. VOICEVOX / 青山龍星（ノーマル） — シャープな男性声、落ち着いている
4. AivisSpeech / コハク（ノーマル） — 自然な男性声、少し柔らかい

ジャービスという装置の体裁上、男性声の 2 つが候補に残り、コハクを選びました。青山龍星はシャープで聞き取りやすく、合成も速い。コハクはより自然で、生活のなかで流しても疲れにくい感じがありました。この選択は好みで、どちらを選んでも設定の 1 行で切り替えられます。

AivisSpeech は生成がやや重いのは事実です。短い応答（1 秒程度）の合成に、CPU で 0.5〜1 秒かかっている印象。これが応答の体感に乗ってきます。VOICEVOX のほうがここは軽い。

## 実機で全段つなげた

コハクに切り替えてから `jarvis listen` を回しました。

```
ウェイクワード検出
認識: 今何時?
< いま夕方の5時37分、月曜日ですよ、ノリさん。
```

スピーカーからコハクの声で返事が来ました。TTS 差し替えは、本当にこれだけで終わりです。

このログで、ついでに 2 つ確認できたことがあります。

**ひとつ、「ノリさん」と呼ばれたこと**。これは Phase 0 の最後に `remember` ツールで覚えさせた名前です。TTS を差し替えたあと、別プロセスで `jarvis listen` を起動したにもかかわらず、名前の記憶は残っていました。`memory.json` に書き込んであるので、プロセスをまたいでも残る。設計の素直な動作ですが、使っていて嬉しい挙動です。

**ふたつ、文単位ストリーミングが TTS 差し替え後も効いていること**。第1回で入れた「LLM の出力を句点が来た時点で TTS に流す」仕組みは、TTS が VOICEVOX / AivisSpeech に変わっても変わらず動いています。1 文目を合成・再生している間に、2 文目の合成が走る。耳で聞くと、応答の最初の音までの体感遅延がだいぶ短くなります。

## 気付いた、2 つの運用上の課題

実機でハマったわけではないのですが、聞き比べをやって気付いた**運用上の弱点**を 2 つ記しておきます。

**ひとつ、TTS エンジンを閉じたら `jarvis listen` の返事は無音になる**（はず）。

VOICEVOX / AivisSpeech は GUI アプリとして常駐しているので、使い終わって窓を閉じると HTTP API も止まります。今日、聞き比べをいったん終えてアプリを閉じたあと、`jarvis listen` を回す前に念のためポートを叩いたら案の定どちらも応答なしでした。今回は閉じているのを分かっていたのでそのまま起動し直しましたが、**走行中にエンジンだけ死ぬと「ログには応答が出るのにスピーカーからは何も聞こえない」という状態になるはず**です。

これは第1回で入れた「API 失敗でプロセスごと落とさない」措置の副作用です。合成が失敗しても会話全体は止めないので、使う側からは「返事はテキストで記録されたのに声だけ出ない」という分かりにくい失敗モードになる。装置として置くなら、

- TTS を Windows の自動起動に入れて常駐化する
- もしくは、TTS 失敗時に OS 標準の音声合成にフォールバックして「TTS エンジンに繋がらないです」と喋らせる

のどちらかは次に入れる価値がありそうです。

**ふたつ、合成のウォームアップに体感差がある**。AivisSpeech の最初の 1 本目は、生成に数秒かかっているように感じました。2 本目以降は早い。VOICEVOX は最初から速い。常時待受の装置では「最初に話しかけたとき」の体験が一番シビアに評価されるので、Pi に載せるときはここで引っかかるかもしれません。

## 設計資産が、また効いた

第3回のウェイクワードのときに「実装は良く設計すると既に書いてある」と書きました。今回も同じことが起きました。

- TTS を差し替えた → `engine` + `options` の構造があったので、コード変更ゼロ
- VOICEVOX と AivisSpeech を切り替えた → 両方とも VOICEVOX 互換 API なので、同じクラスで両方扱える
- 他の段（STT、LLM、ウェイクワード）は無関係に動いた → 段ごとに独立した `interfaces.py` の分離が効いた

積み上がっているものは、積み上がっているものとしてここでも効いています。第1回に書いた「3 つの判断」のうち、文単位ストリーミングは TTS 差し替え後も自然に効き続けた。これは「設計の判断は交換可能な部品の形で入れておく」というメタの話で、記しておく意味があると思います。

## 現在の構成

ここまでで、Jarvis は全段ローカル寄り + Claude というこの形になりました。

- マイク → openWakeWord `hey_jarvis`（ローカル）
- → エネルギー VAD（ローカル）
- → kotoba-whisper-v2.0（ローカル）
- → Claude（クラウド：LLM のみ）
- → 文単位で切る
- → AivisSpeech コハク（ローカル）
- → スピーカー

**音声が家の外に出るのは、ウェイクワード検出後の認識テキストと LLM のやりとりだけ**になりました。第1回で書いた設計の目標が、ここで完成しています。
