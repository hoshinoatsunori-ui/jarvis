# 自作Jarvis 第2回 — S2S を寄り道してみた

第1回では「カスケード（ウェイクワード → 認識 → LLM → 音声合成）を選んだ」と書きました。選んだ以上は選ばなかったほうがどのくらい良いのか、横に並べて確かめておきたくなります。

今回はその寄り道です。Gemini Live API に音声を直接流し込む最小構成を1本書いて、カスケードと聞き比べました。結論から言うと、**第1回の判断は結果的に合っていた**けれど、やってみて初めて見えた細かい話がいくつかあります。

コードは `feat/s2s-gemini-live-prototype` ブランチにあります。
https://github.com/hoshinoatsunori-ui/jarvis/tree/feat/s2s-gemini-live-prototype

---

## 比較のために何を作ったか

カスケード側（本線）は、1発話ごとに段を順に通ります。マイク、ウェイクワード、無音の切れ目を検出する VAD、音声認識、LLM、文単位の音声合成、スピーカー。

S2S はこれを全部 Gemini のサーバで一括してやります。こちらは**マイクを常時 Gemini に流しっぱなしにする**だけ。発話の切れ目はサーバ側の VAD が判定して、応答音声が返ってきたらそのまま再生する。それだけです。

書いたのは1ファイル、300行弱。マイクから拾った 16kHz PCM を 20ms 単位で Gemini に流し、返ってきた 24kHz PCM をスピーカーの再生キューに積む。それだけなのに、カスケード側で第1回に書いた3つの判断（文単位ストリーミング、effort 調整、thinking を切らない）はこの構成では全部不要です。モデル1個が全部やってくれる。

## 動かすまでに1回つまずいた

Google の公式ドキュメントで見かけたモデル名を既定にして動かしたら、こう返ってきました。

> models/gemini-live-2.5-flash-preview is not found for API version v1beta, or is not supported for bidiGenerateContent

モデル名が存在しないか、Live（双方向生成）に対応していない、という応答です。

対処は`models.list` で `bidiGenerateContent` に対応するモデルだけ拾い直すことでした。出てきたのは複数で、ざっくり2系統あります。

- **native-audio 系** （例: `gemini-2.5-flash-native-audio-latest`）: 対話向け。表情を付けて喋る
- **live 系** （例: `gemini-3.8-live`, `gemini-3.1-flash-live-preview`）: より汎用

PoC では native-audio 系を既定にしました。S2S の寄り道の目的は「音声として自然に喋るか」の体感なので。

モデル名の問題というより、**Live に出せるモデルは`models.list` で確認してから選ぶ**という運用の話です。ドキュメントは更新が遅れることがある。

## 動かしてみた

```
15:40:48 認識: こんにちは。
15:40:51 応答: こんにちは。ご機嫌いかがですか?
15:41:08 認識: こんにちは。
15:41:11 応答: こんにちは。ご用件は何でしょうか?
```

ヘッドセットに話しかけたら、音声で返ってきました。認識も日本語で安定しています。

**体感レイテンシは1秒前後**。カスケード側は実機で2〜3秒だったので、明らかに別物です。この差は細かい最適化ではなく、構造の差（中間ハンドオフが無い）から来るので、カスケード側をいくら詰めても埋まらない。

**barge-in も動きました**。モデルが喋っている最中にこちらが話し始めると、サーバ側の VAD がそれを拾って、モデルの応答がぴたりと止まります。カスケード側では Phase 4 の宿題にしていた機能が、S2S ではネイティブに付いてくる。これは羨ましい。

ただし、ヘッドセットを使った前提での話です。ノート PC の内蔵スピーカーだと、再生中の音を自分のマイクが拾ってしまい、サーバが「ユーザーが喋り始めた」と誤判定して応答を止めてしまう可能性があります。エコーキャンセルの問題は S2S を使っても消えません。

## ログを見て気づいた2つの小さい話

### 1. 字幕が storm のように流れてくる

最初に書いたコードは、`input_transcription` と `output_transcription` が届くたびにそのままログに出していました。実際に動かしてみると、こうなります。

```
認識:  
認識: こん
認識: にち
認識: は
認識:  。
応答: こんにちは。 ご機
応答: 嫌
応答: いかが
応答: ですか?
```

認識も応答も、単語単位の partial で届くんです。読めない。

turn 終端まで溜めて1行で吐くように直しました。これで1往復あたり認識と応答の2行で収まります。

### 2. モデルの英語での内心がログに漏れる

native-audio モデルを使うと、`model_turn.parts.text` にこういうのが流れてきました。

```
**Acknowledge the Greeting**
I've registered the user's Japanese greeting. Now, I'm working on
formulating a polite response, also in Japanese, as a suitable next
step. I'm aiming for a greeting that acknowledges their "こんにちは".
```

モデルの内心の英語チェイン思考です。実際にスピーカーから再生されるのは日本語だけで、これはテキスト経路に紛れ込んできただけなのですが、何も考えずに `part.text` を字幕として扱うと、ログに英語の独り言が延々と流れることになる。

字幕としての実体は `output_transcription` のほうなので、`model_turn.parts.text` は無視するようにしました。これ、ドキュメントに書いてあったかどうか記憶にありません。実機で動かすまで見えなかった種類の挙動です。

## それでも本線には取らない

S2S の体感は素晴らしかった。1秒応答、barge-in、表情のある音声。それでも本線（カスケード）に置き換える気にはなりません。理由は2つあります。

**ひとつ、音声が常に家の外に流れる**。マイクをオンにしている間、生の音声が Google のサーバに届き続けます。「ジャービス」とウェイクワードで起こしてから初めて外に出るカスケードとは、プライバシの性格が違う。常時待受の装置を置くなら、ここは引けない線です。

**ふたつ、LLM が Gemini に固定される**。カスケード側では Claude の tool use と MCP の配線を済ませてあり、ここに Home Assistant などの MCP サーバを足せば家電操作に届く設計です。S2S では応答を生成するモデルを選べないので、この設計資産は捨てることになる。

**つまりカスケードの代償（レイテンシ、barge-in の自前実装）は、音声プライバシと LLM の選択の自由を守るための代償だった**ということが、横に並べて初めて明確になりました。

## 寄り道の落とし所

PoC は寄り道フォルダ `experiments/s2s/` に置いたままにしました。消してしまうと、「S2S を試して戻ってきた」という痕跡が消える。ロードマップの比較表には、PoC で実測した「1秒前後」と「2〜3秒」の両方を書き込みました。設計の判断を言葉だけで書いた表に、1回だけ数字が入った。

このブランチは `main` にはマージしません。寄り道は寄り道のまま、独立して残します。本線を触らない PoC は、残しても邪魔にならない。
