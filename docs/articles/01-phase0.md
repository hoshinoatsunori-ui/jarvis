# 自作Jarvis 第1回 — 設計を決めて、実機で一周するまで

家に「ジャービス」を置きたい、という話をします。

映画のあれです。呼びかけると答える。予定を教える。家電を操作する。2026年のいま、これは個人が週末に手を出せる範囲に降りてきています。この連載では、実際に動くものを作りながら、その過程を残していきます。

第1回は**企画と設計、そして最初の一周**まで。マイクに話しかけて、スピーカーから返事が返ってくるところまでを実機で確認しました。

コードは MIT で公開しています。
https://github.com/hoshinoatsunori-ui/jarvis

先に断っておくと、実装そのものは Claude Code に書かせています。私がやったのは、何を作るかを決めること、設計上の判断、そして**実機で動かして壊れ方を見ること**です。そして後述するとおり、最後のひとつが一番大きな仕事でした。

---

## 2026年の選択肢は、実質2つに絞れる

調べていくと、現実的な構成は2系統しかないことが分かります。

**ひとつは S2S（Speech-to-Speech）**。OpenAI の Realtime API や Gemini の Live API です。音声を入れると音声が返ってくる。途中でテキストに変換しないので速い。話しかけて1秒以内に返ってくるし、こちらが割り込んで話し始めれば向こうが黙る、という自然な会話ができます。

**もうひとつがカスケード**。昔ながらの、ウェイクワード検出 → VAD → 音声認識 → LLM → 音声合成、と段を並べる方式です。段が多いぶん遅い。割り込みも自分で実装しないといけない。

普通に考えれば S2S です。速いし、実装も楽です。

それでもカスケードを選びました。

---

## なぜカスケードか

理由はひとつです。**音声認識と音声合成をローカルに置いたまま、LLM だけクラウドにできる**から。

S2S では、マイクが拾った音声がそのままベンダーのサーバに流れます。常時マイクをオンにする装置で、それはどうなのか、という話になる。

カスケードなら、ウェイクワードの検出は完全にローカルで完結します。検出したあとの音声だけを処理し、しかもその音声認識もローカルでやれる。外に出るのは「認識されたテキスト」だけ。日本語の音声合成もローカルで動くものが揃っています。

つまり**音声そのものは家から一歩も出ない**構成が取れる。これがカスケードの唯一にして最大の利点です。

もうひとつ、副次的ですが大きいのは**段ごとに差し替えられる**こと。音声認識が気に入らなければそこだけ替える。LLM を別のものにしたければそこだけ替える。S2S ではモデルが一体なので、この自由度はありません。

代償は正直に書いておきます。割り込み（barge-in）は自分で実装する必要があり、これはまだ作れていません。スピーカーが喋っている最中にマイクを監視し、かつ自分の声を自分で拾わないようエコーキャンセルをかける必要がある。次のフェーズ以降の宿題です。

## 構成

こうなりました。

```
マイク → ウェイクワード → VAD → 音声認識 → LLM → 文に切る → 音声合成 → スピーカー
```

各段の選択です。

- **ウェイクワード**: openWakeWord（ローカル・無料）。開発中は Enter キーで起こす方式も用意
- **VAD**: 音の大きさで判定する単純なもの。静かな部屋なら十分
- **音声認識**: kotoba-whisper-v2.0。日本語に特化した Whisper 派生で、ローカルで動く
- **LLM**: Claude（claude-opus-5）。ツール実行を前提にしたいので
- **音声合成**: VOICEVOX / AivisSpeech。Windows なら OS 標準の SAPI でも通る

音声認識に kotoba-whisper を選んだのは、公式のモデルカードで「large-v3 より日本語の文字誤り率が低く、かつ約6.3倍速い」とされているためです。**この数字は私自身が追試したものではありません**。ただ実機で使った限り、日本語はきちんと聞き取れています。

なお日本語の精度は WER（単語誤り率）ではなく CER（文字誤り率）で見るべき、というのは覚えておくと良い話です。日本語は分かち書きしないので、WER はどのモデルでも高く出て意味をなしません。

## 作るうえで効いた3つの判断

### 1. LLM の出力を、文ができた時点で喋らせる

体感速度を決めるのは、応答全体の長さではありません。**最初の音が出るまで**です。

なので、LLM の出力をストリーミングで受けながら、句点が来た時点でその1文だけ先に音声合成に渡す。全文が揃うのを待ちません。

ここには細かい調整が入っています。句点が遠いときは60文字で見切って読点で切る。逆に「はい。」のような短すぎる断片は次とまとめる（短い音声を細切れに再生すると、かえってぎこちなくなる）。

### 2. effort を下げる

Claude には推論の深さを指定する設定があります。雑談や家電操作に深い推論は要りません。下げると応答が早くなります。

### 3. thinking は切らない

これは罠でした。

速くしたいなら思考を無効化すればいい、と考えたくなります。ところが Claude Opus 5 で thinking を無効にすると、**ツール呼び出しを本文テキストに書いてしまう**既知の失敗モードがあります。つまり「時刻を調べますね」と言いながら実際には調べず、そのまま会話が進む。エージェントとしては致命的です。

速くしたいなら effort を下げる。思考そのものは切らない。

## ツールとMCP

アシスタントとして使うには、LLM が外の世界を触れる必要があります。時刻を調べる、予定を見る、家電を操作する。

組み込みで4つ用意しました（時刻取得、記憶する、思い出す、忘れる）。そのうえで **MCP サーバのツールを設定ファイルに書くだけで追加できる**ようにしてあります。

```yaml
tools:
  mcp_servers:
    filesystem:
      command: npx
      args: ["-y", "@modelcontextprotocol/server-filesystem", "/home/me/notes"]
```

LLM の側から見ると、組み込みツールと MCP ツールの区別はありません。同じ形に変換して渡しています。ここが通っているということは、家電操作（Home Assistant の MCP サーバを足すだけ）に必要な配線が既に済んでいるということです。

## 実機で動かしたら、4回落ちた

ここからが本題です。

コードにはテストが159件あります。ネットワークもマイクも使わず、数秒で全部通る。パイプラインは偽の音声フレームを流して検証し、LLM は SDK を差し替えて「何をいつ呼ぶか」を確かめています。

**それでも実機では4回落ちました。**

しかも全部、「動かない」ではなく**「悪い場所で落ちる」**という種類のものでした。順に書きます。

### 1. Windows で音が出せない

音声合成のエンジンを入れる前に、まず OS 標準のもので通そうとしました。ところがコードは macOS の `say` と Linux の `espeak-ng` しか探していませんでした。**Windows に該当するものが無い。**

PowerShell 経由で SAPI を叩く経路を足して解決しましたが、ここで学んだのは、「最短で通す道」を用意したつもりが特定の OS で途切れていた、ということです。

### 2. 認証エラーで常時待受が死ぬ

API キーが通らないとき、生のスタックトレースを吐いてプロセスごと終了していました。

見栄えの問題ではありません。**常時待受にする以上、通信が一度失敗しただけで死ぬのは致命的**です。混雑（429）でもサーバ障害でもネットワークが一瞬切れても、同じように死ぬ。

API の失敗を「止めるべきか、続けられるか」で振り分けるようにしました。認証エラーやモデル名の間違いは設定の問題なので止める。混雑や一時障害は、そのターンだけ諦めて「混み合っているようです」と喋って待受に戻る。

### 3. 診断コマンドが1.5GBダウンロードし始めた

環境を確認する `doctor` というコマンドを用意していました。各段が動く状態かを一覧するものです。

実行したら、音声認識モデルのダウンロードが始まりました。1.5GB。診断コマンドがやることではありません。

モデルの読み込みを「実際に最初に書き起こすとき」まで遅らせました。ただしこれには副作用があって、そのままだと今度は**最初に話しかけたときに長い沈黙が入る**。なので待受に入る前に読み込むようにしました。診断は軽いまま、会話は止まらない。

### 4. 最初に話しかけた瞬間に死ぬ

これが一番厄介でした。

音声認識の実行先を `auto`（自動選択）にしていました。GPU があればそちらを使う、という設定です。私の環境には GPU がありましたが、CUDA のライブラリが入っていませんでした。

問題は**落ちる場所**です。モデルの読み込みは成功する。待受も始まる。そして**最初に話しかけた瞬間**に、ライブラリが見つからないと言って会話ごと死ぬ。

直し方は2つ入れました。起動時に短い無音を1回通して、推論の経路が本当に生きているかを確かめる。そして `auto` を指定しているなら、GPU が使えなければ CPU に落とす（`auto` は「選んでくれ」という指定なのだから、それが期待される動作のはずです）。ただし `cuda` と明示した人には黙って落とさずエラーにします。GPU を使いたい人が気づけないので。

## テストは何を担保していたのか

4件とも、テストでは見えませんでした。当然です。テストは「マイクもネットワークも無い環境で動くこと」を前提に書かれていて、まさにその前提の外側で起きたことだからです。

ただ、テストが無駄だったわけでもありません。実際、実装中にテストが2件の不具合を捕まえています（MCP の接続がツール一覧取得の直後に切れる、というものと、長文のときに発話が始まらない、というもの）。

分かったのは役割分担です。**テストは「呼び方」を守り、実機は「壊れ方」を教える。** そして後者は、実際に動かすまで絶対に見えません。

## 現在地

Windows 11 + VS Code で、通しで動いています。

```
[Enter で話しかける]
ウェイクワード検出
認識: 今日は何日?
< 今日は2026年9月27日、日曜日ですよ。
< 今は夕方の6時12分ごろです。
```

日付も時刻も正確です。これは LLM が知っていたのではなく、**時刻取得ツールを実際に呼んで答えている**ということです。応答が2文に分かれているのは、文ができた時点で喋らせる設計が効いている証拠です。

まだ実機で見ていないものも書いておきます。ウェイクワード検出（今回は Enter で代替）、VOICEVOX（OS標準の合成で代替）、そして macOS と Linux の経路。
